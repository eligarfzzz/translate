# Session reuse — per-slot conversation chains, accumulated client-side

Each host is still translated by its own request ([ADR-0005](./0005-per-host-request.md)), but with `reuseSession` on (「重用会话」, a checkbox on the options page's API tab, **off by default**) each concurrency-pool worker keeps one conversation chain: the segments that slot has already translated successfully are replayed to the model as the history of the next request, and the model translates only the newest segment. The motivation is translation quality, not throughput — a page translated as N independent stateless requests makes the model restart from zero on every paragraph, so the terminology and style of a region drift paragraph by paragraph; replaying the slot's own earlier (original, translation) pairs keeps them consistent. Off is the default, and the request shape is unchanged there: one host, one independent stateless request, no `history` field. The one behaviour change that reaches the off state is the shape trigger's retry described below.

The chain is plain `messages` accumulated **client-side**. The content script holds a slot's history as pure data — `{ html, echo }` pairs, html being that segment's skeleton HTML and echo the model's raw reply — and sends it along with the `start` port message (a new optional `history` field); `background.js` assembles the request body from it at send time, wrapping each replayed user turn with the same helper that injects `{host}` (`prompt.js` is the single source of the wrapper form). **No server-side session id, no gateway-private conversation feature**: the endpoint stays a plain stateless chat-completions call whose request happens to carry more messages. The rejection is deliberate on both ends. A server-side session would move the state out of our reach — into a store we neither own nor can release per page — and, for a gateway whose session support is a vendor extension, would make the extension depend on one particular gateway. Keeping chains in `background.js` was rejected for a different reason: it is shared by every tab, so chains there would need a (tab, generation, slot) key and a guaranteed release path, which is inventing cross-tab bleed and leaks. In the content script the chain dies with the page, for free.

A chain belongs to a pool worker, not to the page and not to document order: with `concurrency` N there are at most N independent chains, and a segment carries only the successes of its own slot — six segments `abcdef` with concurrency 3 run as `a→d`, `b→e`, `c→f`. One worker appends to one chain, so no two requests race to define "the previous segment". A chain is created with the pool that runs a round of translation and dropped when that round ends (the next round — e.g. a rescan's pass — starts fresh chains), so 还原 or a page refresh discards the history, and turning the option on or off takes effect on the next round — never inside a chain already in flight. The request-time config (template, endpoint) is still read per request as before ([ADR-0003](./0003-hardcoded-config-with-ui-seam.md)); what never changes mid-flight is the chain itself. Concurrency, priority ordering, per-host settle and the progress badge's counting are all untouched by the option; only the request bodies grow. That growth is the accepted cost — terminology consistency is what the option buys — and it is quadratic in page size: a chain of length k re-sends all k−1 earlier turns, so translating a whole page costs O(n²) input tokens overall; the default 20 workers bound it to 20 chains at a time, and a user who does not want the cost leaves the option off.

**Failed segments never enter the chain.** The chain is exactly its slot's successful segments in order; a segment that ends in an endpoint error, a dropped connection, or an empty echo pushes no turn, and the next segment on that slot carries the history up to the last success — a failure costs the slot its context, not its correctness. The chain head — a slot's first segment, or a fresh session after a retry — is today's request byte for byte (one user message, rendered template plus that segment), so enabling the option cannot change how the first request of a slot is made.

**Two triggers, one fallback, one retry each.** A long chain has two known failure modes and they share the same recovery: drop the history and retry the segment once as a new session (chain head, no history). Trigger one is shape drift — a 200 response whose non-empty body is not exactly one `<html>…</html>` wrapper, the same predicate `stripHostWrapper` uses (no second standard for "what is a wrapper"). Such an echo used to be rendered leniently, junk and all; it now retries, and if the retry is also off-shape the segment takes the ordinary error path instead of writing garbage into the page (the content-side lenient path stays as defence in depth, no longer reached in normal operation because background stops off-shape echoes before they get there). Trigger two is the context limit — the endpoint returns an error whose text matches a conservative, case-insensitive list of phrasings (`context length`, `maximum context`, `context window`, `token limit`, `too many tokens`), which is hardcoded and not configurable, to be extended as the gateway's wording evolves. It retries only when the request actually carried history: a chain head is the stateless request, so resending it would change nothing. Empty echoes (`""` / `<html></html>`) are never retried — they keep the existing 「未返回译文」 error. Both retries happen inside `background.js`: content sees exactly one `done` or one `error` per host and never an extra settle, so the badge's counting discipline is unaffected, and a retry that succeeds makes that segment the slot's new chain head, so the abandoned history is not carried forward. The port protocol gains one control message besides the optional `history` field: `restart`, sent before a retry, because a streamed preview cannot be retracted — content clears the failed attempt's text and the chain it had accumulated, so the finalized translation and the echo that enters the chain come only from the attempt that succeeded. One risk is recorded and left unimplemented: on a very long chain a model may stop imitating the translation pattern (which is what the shape trigger detects). The recorded fallback is a `system` message repeating the template each turn; since the retry above is the first-line recovery for exactly that drift, the fallback stays on paper until a real case shows the retry is not enough.

## Relationship to ADR-0005

ADR-0005's "one host, one request" is the **success path's** counting discipline — every host is one port, one upstream request, one settle, and the whole reply is that host's translation. A failure-recovery retry is an extra upstream request on the failure path, invisible to the counting: it rides the same host request, posts no second `done`/`error`, and produces no second settle. The two decisions therefore do not conflict, and ADR-0005's text is left as written — this decision adds an optional request shape and a retry, not a second request model.
