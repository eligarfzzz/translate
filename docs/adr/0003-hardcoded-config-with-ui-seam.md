# Hardcoded config with a config-UI seam

All API settings (endpoint, key, model, target language) are hardcoded in `config.js`, with a clearly marked seam for a future config UI (a `getConfig()` accessor every consumer calls, never raw constants). This keeps v1 shippable without a UI while making the future migration mechanical. The API key is visible to anyone who installs the extension — accepted for v1, but the key must never be a production credential.

---

**Fulfilled.** The config UI shipped (options page, opened by left-clicking the toolbar icon): consumers now call the async `loadConfig()`, which type-defensively merges `chrome.storage.sync` overrides over the in-code defaults via the pure `mergeConfig()`. The seam held as designed — the migration was mechanical and no consumer ever touched raw constants.

---

**Evolved: zero-trace defaults.** The in-code defaults for endpoint, key, and model were cleared to empty placeholders — the repo now carries no real endpoint, key, or model name in code, tests, or docs, so a fresh clone yields no usable credentials. Real configuration is entered on the options page and lives only in `chrome.storage.sync`; it never produces a repo file. An unconfigured translate click rejects each batch up front through the existing batch-error channel with a "open the config page" pointer instead of a vague network error. Scrubbing the values from git history remains the owner's separate task.

---

**Evolved: `promptTemplate` is a plain default key — frozen-template users exist.** When the prompt template became an ordinary entry in the defaults table (ESM refactor, ticket 06), anyone who had *saved* the then-current default template in `chrome.storage.sync` before that change keeps overriding every future default with their stored copy — they are frozen on the old default. Anyone who never saved a template gets each new default automatically. Consequence for the future: changing the default template does not reach frozen users; to reach them they must clear the field on the options page (or remove the stored `config`). Affects only the template key; other keys whose defaults changed have the same property, but the template is the one likely to evolve.

---

**Evolved: the options page is TAB-grouped, and "恢复默认" became a per-group form fill.** The page now has three TABs (API / 提示词 / 通用), each with its own "恢复默认" button. That button fills only its own TAB's inputs with the in-code defaults and writes nothing; 保存 still writes every field of every TAB as one `config` blob, so the storage key remains a single whole-blob write from one place. The per-group scope is what forced the change: a group-scoped button that deleted the shared `config` key would reset the other TABs too.

Two consequences for the note above. The escape hatch "(or remove the stored `config`)" no longer has any UI affordance — no button deletes the key, so that route is now DevTools-only. Worse, the intuitive gesture 提示词 → 恢复默认 → 保存 *freezes* the user onto today's default template, the exact state the note warns about, because it writes the default's literal text into storage. The un-freeze route is unchanged and remains the only one: clear the textarea, then 保存 (an empty string falls back to the default at runtime while `mergeConfigRaw` keeps showing it empty).

---

**Evolved: empty means unset — the two read semantics collapse into one and "恢复默认" becomes the unfreeze path.** A config field left empty is now unset rather than a value. 保存 rewrites the whole `config` blob from the normalized form values, so an empty field's key is deleted (an all-empty form deletes the `config` key itself); reading starts from the full in-code defaults and overlays only the non-empty stored values; the options page fills each box only from what is really stored, shows an empty box otherwise, and displays the field's default as its placeholder (a descriptive fake example for the three empty-string API defaults, keeping the repo zero-trace). The per-group 恢复默认 button clears that group's inputs without writing anything — 清空 + 保存 = 删键 — so the freeze the note above warns about (恢复默认 → 保存 writing today's default literal into storage) is gone: the group now follows every future default. The UI-only raw/runtime read semantics are removed (`loadConfigRaw` / `mergeConfigRaw`, "fill the box with exactly what was saved"), leaving one normalization entry point in `config.js` that decides emptiness for both the read and the write path, per default-value type: strings must be non-blank after trimming, numbers must be finite positive integers, and the prompt template must contain `{host}`. Pure whitespace and wrong-typed values are consequently no longer treated as values — previously pure whitespace passed through into prompts (or produced a broken endpoint URL) and a non-blank template missing `{host}` silently fell back to the built-in one after a save-time notice. The original decision is unchanged — zero-trace defaults, sync-storage override of the in-code defaults, and the single config seam all still hold; this narrows what counts as a stored value rather than revising the decision.

---

**Evolved: `extra` (追加提示词) feeds a `{extra}` placeholder in the default template, and placeholder examples stopped being mandatory.** The defaults table gained `extra`, a free-text key (「追加提示词」 on the options page, a 4-row textarea) that renders into a new `{extra}` placeholder the default template now carries alone on its own line, between "Output exactly one translated copy of that fragment." and "Example: …"; unset — its default, like the three API fields — renders that line empty, so not filling it in changes nothing. It only resolves on templates that contain the placeholder: a user frozen on a custom template without `{extra}` (the frozen-template note above) gets no effect from 追加提示词, silently — no placeholder is inserted into their template and no save-time notice is shown. Placeholders written inside 追加提示词 stay literal (`{target}`, `{host}`, `{extra}` all render as written), because `renderPrompt` now scans the template exactly once and looks each placeholder up in the vars table instead of re-scanning its own output once per key; that same change stops injected input from being re-interpreted — a host whose text contains a literal `{target}` used to have it silently replaced with the target language. The placeholder rule narrowed to one sentence as well: a field with a non-empty default shows that default as its placeholder, while an empty-string default *may* carry a descriptive fake example — examples are optional field knowledge now, not a mandatory companion of every empty-string default (the three zero-trace API fields keep theirs). 保存's feedback was reworded in the same change: it reports only the keys that existed in the normalized storage before the write and are absent from the payload — the settings really cleared — instead of counting every blank box on the form, so a user who only edits the API group is no longer told that settings were deleted. The original decision is unchanged; `extra` is an ordinary default key, so it saves and clears by the same rules as every other one.
