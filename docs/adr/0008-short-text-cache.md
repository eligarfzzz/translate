# Short-text cache — background IndexedDB, fingerprinted keys, hit-refreshed LRU

Short hosts — nav items, buttons, footer links — recur verbatim across pages, and under one-host-one-request ([ADR-0005](./0005-per-host-request.md)) each recurrence costs a full streaming request carrying the whole instruction header: a 30-byte original pays the same template and round-trip as a paragraph. Short originals (skeleton HTML of at most `cacheMaxBytes` UTF-8 bytes, default 30, tags included, no `<html>` wrapper) are now served from a cache: looked up before any upstream call, written back on a miss that ends in a fully successful, well-wrapped, non-empty echo. The motivation is request count, not latency.

The store is one IndexedDB database owned by the **background service worker**. The two alternatives were rejected for structural reasons. **Content-script IndexedDB** belongs to the *page's* origin: the cache would fragment into one database per translated site — readable and writable by that site's own scripts — with zero cross-page sharing, which is the entire point of the cache. **`chrome.storage.local`** (already used for the log ring) is a flat key-value store: expiry by age and eviction to a cap need a `lastUsedAt` index to scan, which there means maintaining a parallel metadata record read and rewritten on every pass — reinventing an index, badly. IndexedDB provides the index, the cursor, and the extension-origin scope natively.

Lookup and write both live inside the background `start` handler, after the unconfigured guard (the key's fingerprint needs the loaded config) and before the fetch. A hit posts one `delta` carrying the cached raw echo followed by `done`, so the content script's preview/finalize path, the per-host settle收口, and the progress badge's counting all observe an ordinary fast reply with **no second code path**. Putting the lookup in content instead would have meant a query round-trip ahead of the port plus a duplicate settle/render branch for hits — rejected. The stored echo is the raw reply, wrapper included — the same bytes a live reply would have streamed — so the hit path reuses `stripHostWrapper` and sanitization unchanged. To make the echo available for storage, `requestWithRetry` now returns the winning attempt's accumulated text, which was previously internal to the retry loop; the port protocol is otherwise untouched except for one optional flag.

That flag: `done` may carry `cached: true`. Its only consumer is the 会话重用 chain ([ADR-0007](./0007-session-reuse.md)). With `reuseSession` on the cache is still queried and written (a cached translation may carry another context's style — accepted), but a **cached segment never enters the slot's chain**: cached text is never replayed to the model as something it said itself. Misses enter chains exactly as before, and a slot whose early segments were all cache hits simply starts its chain at the first miss.

Keys are `fingerprint + skeleton HTML`, where the fingerprint hashes the five request-shaping config values — apiBase, model, targetLang, promptTemplate, extra. Changing any of them strands old entries (they expire naturally) instead of serving stale-language translations, so the cache never needs explicit invalidation on save. The apiKey is deliberately *not* fingerprinted: the key does not shape the translation. The hash is one-way, so the zero-trace posture ([ADR-0003](./0003-hardcoded-config-with-ui-seam.md)) is unaffected.

Expiry is **LRU with hit refresh**, not write-TTL: each entry holds one `lastUsedAt`, set on write and refreshed on every hit; an entry dies only after `cacheTtlDays` (default 30) *unused*, and when the store exceeds `cacheMaxEntries` (default 10000) the oldest-used are evicted down to the cap. Both run in a single cleanup pass triggered once per session — the content script messages background after the initial round's hosts have all settled, only while the cache is enabled; rescans do not retrigger it, and with the cache off no cleanup runs at all. The cap is enforced only in that pass, so the store may overshoot `cacheMaxEntries` by at most one round's worth of short hosts — accepted. Identical originals within one round are not coalesced in flight: N copies of the same new short string still cost N requests the first time — accepted for v1.

Two consequences worth recording. **`cacheEnabled` defaults to on**, which the old boolean rule could not express — only the literal `true` was storable, so a default-true checkbox could never be turned off. Normalization was generalized to its mirror form: a boolean stores only the *non-default* face (a `false`-defaulted field stores only `true`, a `true`-defaulted field stores only `false`), everything else is unset. `reuseSession`'s behaviour is byte-identical, and "return the box to the default state + 保存" is the checkbox form of 清空 + 保存 = 删键. All four keys live on the options page's 通用 tab, and the three bounds are ordinary positive-integer keys (`cacheMaxEntries` / `cacheTtlDays` / `cacheMaxBytes`); changing them never rewrites existing entries — a smaller cap or shorter TTL takes effect at the next cleanup, and a changed threshold only gates future lookups and writes. **IndexedDB failure degrades, never blocks**: any error opening or using the database is logged and translation proceeds uncached; a cache fault never surfaces as a page-visible error.

---

**Evolved: the store can be emptied on demand, and that one action answers back.** The options page's 通用 tab gained a 「清空缓存」 button, sitting with the other non-submitting action buttons (导出日志 / 清空日志) rather than among the settings, so it is not read as something 保存 would apply. It clears the *whole* store, not the entries under the current fingerprint: entries stranded by an earlier config change are already invisible to the user, and leaving them behind after an explicit clear is the worse surprise. It runs regardless of `cacheEnabled` — the switch governs the automatic path (lookup, write, scheduled cleanup), and the user who just turned the cache off is the likeliest one to want its leftovers gone. The action travels over a new `clear-cache` runtime message to the background worker instead of the options page opening IndexedDB itself, keeping the database/store/version names in the store module alone; `cleanup-cache` was left as its own message because the two differ in caller, timing, and contract — a request that answers with the pre-clear count versus a fire-and-forget notification from the page. The store gained a single-transaction count-then-clear. This is also where the no-page-visible-error posture narrows: an IndexedDB fault still never surfaces during translation, but an **on-demand** clear reports either the number of entries removed or a failure, because a silent no-op — or a false "cleared" — in reply to an explicit user action is worse than an error message. A clear is not a barrier: requests already in flight still write their successful results afterwards, so entries can reappear — accepted, since voiding them would take a cross-tab generation broadcast far larger than the button itself.

---

**Evolved: the store is inspectable, and each entry counts its actual hits.** The options page's 通用 tab shows the whole store in a read-only table — skeleton original, raw echo, cumulative hit count and last-used time — twenty entries at a time, newest-used first. The listing deliberately covers every fingerprint and works with `cacheEnabled` off, matching manual clear's scope: stranded entries still occupy storage, so filtering them out would misrepresent what is actually there. A dedicated request–response message keeps the options page away from database schema knowledge. Pagination reuses the `lastUsedAt` index in reverse and recovers the original from the cursor's primary key rather than duplicating it in every value; requested pages beyond the current end clamp to a valid page, while an empty store returns an empty first page. The store caps a page at one hundred entries and answers with the effective size, so an abnormal caller cannot pull the whole store in one request. Entering the tab reloads the first page, and a successful clear reloads it again; clicking the already-selected 通用 tab is a no-op after a successful read but retries page one after a failed read, so the table remains recoverable without switching tabs. Live cross-tab refresh and snapshot isolation between page requests are intentionally not provided.

A hit count is per cache key, not per echo generation. New keys start at zero, an actual hit increments the count in the same transaction that refreshes `lastUsedAt`, and a miss does nothing. An overwrite preserves the existing count so duplicate in-flight requests cannot erase hits that happened before their writeback; deleting a key through clear, expiry or eviction loses its count with the entry, so a later recreate starts at zero. Entries written before this feature have no count field and are read as zero — there is no historical backfill. Because the count is an ordinary value field and listing adds no index, the database version stays unchanged and no migration pass is needed. This is per-entry usage information, not a hit-rate panel: misses remain unrecorded. As with manual clear, an explicit listing failure is reported to the user rather than disguised as an empty store; cache failures during translation remain silent. Original and echo are rendered strictly as text, so cached markup cannot become live options-page HTML.
