# Spec: 翻译优先级——边缘区域排到请求队尾

Status: ready-for-agent

## Problem Statement

一次会话里，宿主发现按文档序返回（`discoverEntries` 的 DFS 顺序），而页眉、页脚、导航、侧栏在 HTML 里通常排在正文**之前**。并发池按数组下标取任务，于是页面上宿主数超过并发上限（默认 20）时，前 20 个请求大量被导航链接、页脚版权、侧栏栏目名占据，读者最关心的正文反而要等边缘区域腾出并发位才开始翻。体感是「点了翻译，先看到导航变成中文，正文迟迟不动」。

## Solution

宿主发现的出口给每个宿主判一个**翻译优先级**档位，按档位稳定排序后交给并发池：

- 档 0 正文区域：`main` / `article` / `[role=main]` 之内
- 档 1 未标记：不落在任何区域标记内（与今天的行为一致）
- 档 2 边缘区域：`header` / `footer` / `nav` / `aside` 及等效 role（`banner` / `contentinfo` / `navigation` / `complementary`）之内

档位由**离宿主最近的**区域标记决定：`main > nav > p` 判边缘（它确实是目录/面包屑），`aside > article > p` 判正文。档内保持文档序。

这只改变请求发起顺序，译文节点的插入位置仍由宿主自身决定（ADR-0002：追加到宿主末尾），页面版面完全不受影响。

## User Stories

1. 作为长文页面的读者，我希望点下翻译后正文段落先出译文，这样我能立刻开始读，而不必等导航和页脚翻完。
2. 作为读者，我希望页眉页脚导航最终**仍然会翻**，只是排在后面，这样我不会因为优先级而丢失内容。
3. 作为读者，我希望译文出现的位置不因排序而改变——每段译文仍紧跟在它自己的原文下面。
4. 作为读者，在宿主总数少于并发上限的小页面上，我不应察觉任何行为变化（所有请求几乎同时发出）。
5. 作为读者，`main` 里的目录/面包屑导航应被当作边缘区域，这样正文段落不会被目录里的几十条链接挤到队尾。
6. 作为读者，被塞进侧栏的 `article`（相关文章正文）应被当作正文，因为它离宿主最近的标记说明了它自己是什么。
7. 作为读者，使用 `div role=navigation` 而非 `<nav>` 的站点也应正确降档，这样不写语义标签的站点同样受益。
8. 作为读者，会话期内动态新增的内容（SPA 路由、懒加载、折叠展开）在重扫轮内同样按优先级排序。
9. 作为扩展 owner，我希望首轮日志能报出各档宿主数，这样我能验证排序确实生效——排序是纯时序行为，页面上看不出来。
10. 作为扩展 owner，我希望档位随宿主条目一起流出发现模块，这样判档逻辑可以被直接断言，而不必从数组顺序反推。
11. 作为扩展 owner，我希望区域标记表是源码里的硬编码常量，与既有的硬跳过选择器放在一起，因为这是 HTML 语义事实而非用户偏好。
12. 作为扩展 owner，我希望排序不引入新的会话状态、不影响还原语义，这样安全边界（会话代号作废）保持原样。
13. 作为扩展 owner，我希望宿主资格判定、快照序列化、回显净化三处逻辑一字不改，这样本次改动的风险面只有排序。

## Implementation Decisions

- **判档时机在宿主发现的出口**，与宿主条目一同产出。首轮与重扫共享同一出口，调用方无需分叉判断，也少一处将来会忘记同步的地方。
- **判档算法是自宿主自身起的一次祖先链上行**，逐级先试正文选择器再试边缘选择器，首个命中即返回；走到根仍无命中判未标记。这是「最近祖先胜出」的直译，且与传入的子树 root 无关——若将来只重扫某子树，root 以上的祖先标记不会丢。备选方案（DFS 下行时把档位当参数传递）零额外遍历，但埋了「传 root 就静默错档」的坑，故不取。
- **档位是宿主条目的一个字段**（条目从 `{ el, html }` 扩为 `{ el, html, tier }`），不是排序后即丢的临时量。判档与排序因此可以分开观测。
- **排序稳定**，依赖 ES2019 起 `Array.prototype.sort` 的稳定性保证档内文档序，不额外记录下标。
- **区域标记表硬编码**为发现模块内的选择器常量，与既有的硬跳过、安全块白名单常量并列；不进配置中心，不上配置页。
- **标签与 role 等价**：两类写法合成一张选择器表，因为大量站点用 `div role=navigation` 而不用 `<nav>`。
- **首轮日志追加分档统计**（形如 `tiers 12/30/5`）。重扫日志不动：每轮宿主少，加了噪音大于信息。
- **不写 ADR**：三条门槛（难以逆转 / 无背景会困惑 / 真实取舍）只中第二条，改回文档序只需删掉一次排序调用。CONTEXT.md 补两条词条与一条规则即可。

## Testing Decisions

- **只有一道缝**：宿主发现的出口。档位既然随条目流出，判档就能被直接断言，无需为判档单独开一个导出——缝越少越好，也不必为测试放宽模块的私有边界。
- **测外部行为**：断言「某宿主的档位是什么」与「条目数组的顺序是什么」，不断言祖先链是怎么走的、选择器表长什么样。
- 覆盖的分支：正文/未标记/边缘三档各一例；`main > nav` 判边缘与 `aside > article` 判正文（最近祖先胜出的两个方向）；`div role=navigation` 与 `<nav>` 等效；一个混合页面断言顺序为正文→未标记→边缘且档内保持文档序。
- **沿用既有夹具**：发现模块的测试已有 jsdom 夹具（inline style 驱动 display、`getBoundingClientRect` 仅测试内 stub）与显式安全块常量，新用例直接复用，不新建夹具、不改动任何既有用例。判档不依赖真实布局，jsdom 完全够测。

## Out of Scope

- **过滤**：让边缘区域根本不翻。本 spec 只排序，所有宿主最终都会翻。
- **配置化**：把区域标记表或分档策略暴露成配置项。
- **并发池调度策略**：仍是「按数组下标取任务」，不引入优先级队列、不做运行中抢占。已发出的请求不会因为后来发现了更高档的宿主而被打断。
- **译文节点位置**：插入语义（ADR-0002）不变。
- **重扫轮之间的全局优先级**：排序在每轮之内。上一轮的边缘区域不会与下一轮的正文重新混合排序。
- **视口可见性优先**：按滚动位置或视口内外排序是另一条思路，本次不做。

## Further Notes

- 排序的可观察效果与并发上限直接相关：宿主数不足并发上限时全部几乎同时发出，排序无从体现。验证时应选长页面，或临时压低并发数。
- 「最近祖先胜出」的代价是每宿主一次祖先链上行。相对每宿主一次 LLM 请求，这个开销可以忽略。
- 正文选择器里的 `main` / `article` 同时也在「更深块存在则下探」的常见块集合内，两处语义不冲突：下探决定宿主粒度，判档决定请求次序。
