# Spec: 缓存手动清空（cache-manual-clear）——配置页一键清空短文本缓存库

## Problem Statement

- 短文本缓存（ADR-0008）目前**只有自动维护**：过期与 LRU 淘汰在一次翻译会话的首轮全部落定后跑一次，由 content 侧发一条 `cleanup-cache` 触发。用户没有任何手动手段。
- 想立刻释放空间、想把某次不合意的翻译体验复位、或想确认缓存里到底还留着什么，唯一路径是 DevTools → Application → IndexedDB → 删库。对非开发者这等于没有这个能力。
- 旧 spec 明文把手动清空写在 Out of Scope 里（「DevTools 可清；等真实需求再加」）。需求到了：清空应当是配置页上的一个动作，而不是开发者工具里的一次手工操作。

## Solution

配置页「通用」TAB 增加一个「清空缓存」按钮。点击即清空**整个短文本缓存库**（全部条目，不只是当前配置指纹那批），状态栏回显本次清掉了多少条。清理立刻生效：不需要保存设置、不需要重载页面、不需要重启浏览器。按钮不参与表单提交，不写任何配置，不触碰日志，也不终止正在进行的翻译——页面上的译文不会因此消失或报错。

## User Stories

1. 作为用户，我想在配置页一键清空缓存，这样我不用打开 DevTools 去 IndexedDB 里删库。
2. 作为用户，我想在点击后立刻知道清掉了多少条，这样我能确认按钮真的生效了，而不是靠猜。
3. 作为用户，我想清空时不被迫先保存设置，因为它不是一个设置项，而是一个动作。
4. 作为用户，我想在关掉缓存开关后仍能清空残留条目，否则我关掉开关后就再也管不着库里存的东西了。
5. 作为用户，我想清空不影响正在进行的翻译，页面上的译文不消失、不报错、进度徽标不乱。
6. 作为用户，我想清空不惊动其他标签页的翻译会话——那些页面只在下次查询时自然未命中，不会被打断。
7. 作为用户，我想清空失败时看到明确提示，而不是以为已经清了、实际什么都没发生。
8. 作为用户，我想在空库上点击也看到成功提示（0 条），而不是怀疑按钮坏了。
9. 作为用户，我想这个按钮不要被误认为属于「保存」的一部分，点它不该写配置、也不该被 TAB 切换影响。
10. 作为用户，我想清空是可再生的操作（清掉只是以后多花几个请求），所以不要用确认弹窗打断我。
11. 作为用户，我想清空之后原来命中的短文本重新走上游请求，并且结果照常渲染、照常进入会话链（走完完整未命中路径）。
12. 作为开了「重用会话」的用户，我想清空不影响当前槽位已经积累的会话链——链是页面上下文里的东西，缓存清空不该动它。
13. 作为用户，我想清空是一个动作要么全成要么报错，不要出现「清了一半」这种我看不出来的中间态。
14. 作为用户，我想清空之后重新翻译时缓存会重新积累，不需要额外操作。
15. 作为用户，我想清空只清缓存，不动我的配置、不动运行日志。
16. 作为维护者，我想清空与自动清理共用同一份数据库 schema 知识（库名 / 版本 / store 名），不要在第二处再硬编码一遍。
17. 作为维护者，我想手动清空与自动清理保持各自的契约（一个是用户请求要回应，一个是页面发出的通知不需要回应），不要为了少写一条消息把它们混成一个带模式参数的双用途消息。
18. 作为维护者，我想这条新消息在扩展的零痕迹约定下依然干净：不出现真实端点、密钥或厂商模型名。

## Implementation Decisions

- **D1 清空范围 = 整个库**：清空全部条目，不做「只清当前指纹那批」。理由：改过配置而残留下来的条目对用户本就不可见（永远命不中），一次显式的「清空」之后它们还留在磁盘上，是比多清更坏的意外；而只清当前指纹会让用户点了按钮却看到库里仍有东西。「按指纹选择性清空」留作将来真有需求时的增量。
- **D2 按钮形态与位置**：「通用」TAB 的按钮行末尾（`恢复默认` / `导出日志` / `清空日志` / `清空缓存`），文案「清空缓存」，`type="button"`，`id="clear-cache"`，**不带 `name` 属性**。这一行都是不参与「保存」的一次性动作按钮，聚在一起不会被误读为「保存时才生效」的设置项；而两个反向守门测试要求表单里的每个 `name` 字段都必须在默认值表的键里、且每个默认值键都必须有同名字段，所以动作按钮绝不能带 `name`。
- **D3 执行位置在 background**：选项页只发一条新的 runtime 消息，由 background 侧调用存储模块执行清空。选项页**不**自己去 `indexedDB.open(...)`——库名 / 版本 / store 名这份 schema 知识必须只出现在存储模块一处，这既是本仓库既成的结构（background 独占 IndexedDB），也是 D1 之外不产生第二份事实来源的前提。
- **D4 新增独立消息，不改造 `cleanup-cache`**：消息契约——请求 `{ type: "clear-cache" }`；响应 `{ ok: true, removed: N }` 或 `{ ok: false, removed: 0 }`（失败时页面按统一文案提示，不需要区分故障种类）。不复用 `cleanup-cache` 加 mode 参数：两者的调用方（选项页 vs content）、时序（用户点击时 vs 会话首轮落定后）与响应契约（请求-响应 vs fire-and-forget 通知）都不同，混成一条只会让两个调用方互相约束。background 侧的处理挂在既有的缓存消息监听器上（同一主题的消息聚在一处），该分支保持回应通道打开（异步 reply）。
- **D5 存储模块新增 `clear()`**：单事务内先取条数再清空（避免两次事务之间被并发写入把数字搞歪），返回清空前的条数与成败；空库返回 0 且视为成功。
- **D6 与开关无关**：`clear-cache` 的执行**不读** `cacheEnabled`，未勾选/已存 `false` 时照常清空。开关管的是自动链路（自动查、自动写、定时清理）；手动清空是用户的显式意图，而刚关掉缓存的用户恰恰最可能想清掉它留下的东西。落地含义：这条消息不加载配置。
- **D7 失败必须可见（本功能对 D10 的唯一例外）**：IndexedDB 打不开或清空失败时，选项页状态栏显示失败文案（不含技术细节，细节进日志），并且 background 侧记一条错误日志。ADR-0008 的 D10 管的是**翻译流程中的静默降级**——用户当时并没有在做缓存这件事，页面上冒一条缓存错误只会让人困惑；而这里是用户主动点了按钮：按钮毫无反应、或假报「已清空」，才是真正的问题。这条边界同时写进 CONTEXT 词条与 ADR 的 Evolved 段。
- **D8 清空不是屏障（在途写入会复活）**：清空执行那一刻已经飞出、随后成功返回的请求仍会写回缓存，条目会重新出现。接受，并作为已知语义记录：要作废在途写入需要一套跨标签页的暂停/失效广播（新消息类型 + 生成代数计数），代价远大于收益；缓存的下一轮自动清理仍会兜住容量。清空也**不影响**任何标签页当前会话里的会话链——链在页面上下文的内存里，不属于缓存。
- **D9 不加二次确认，不去抖**：缓存可再生，同族的「清空日志」也是点了就清；加确认只会让这个按钮看起来比它清除的东西更危险。连续点击不是问题：第二次照常回「（0 条）」。
- **D10 不写配置、不需要保存**：按钮不触发任何存储写入（`chrome.storage` 一字不碰），也不需要先点「保存」；TAB 切换到别的面板不改变它的可用性。
- **D11 content 侧零改动**：本功能只新增选项页 → background 的一条消息；content 的端口协议、清理触发时机、渲染路径、进度徽标全部不变。清空后的下一次翻译自然走未命中路径，与「第一次遇到这段短文本」逐字节同形。
- **D12 清空后不重跑本轮自动清理**：D7（既有 spec）的清理触发是每会话恰好一次，与手动清空互不干涉；手动清空之后本会话不会再补一次自动清理。
- **D13 零痕迹**：代码 / 测试 / 文档不出现真实端点、密钥、厂商模型名；测试里的库内数据一律是假值。

## Testing Decisions

- 好测试的标准沿用仓库口径：只断言外部可观察行为（runtime 消息的载荷与次数、状态栏文案、存储里的条目、日志留痕），不断言内部状态。
- **存储模块**：既有 `tests/cache-store.test.js` 的工厂注入接缝（假 IndexedDB）。需要给 `tests/helpers/fake-indexeddb.js` 补一个 `objectStore.clear()`（现有假实现只有 get / put / count / 索引游标）。新用例：多条条目清空后全部未命中、返回值等于清空前的条数、空库返回 0、IndexedDB 故障时返回失败态且日志有记录（不抛异常，与既有 D10 收口一致）。
- **background 集成**：既有 `tests/helpers/background-sandbox.js`（chrome / fetch / 端口 / 假 IndexedDB）。新用例：发 `clear-cache` → 库清空且回应条数正确；`cacheEnabled: false` 时**照样**清空（D6，这条是本功能最容易被写错的分支，需专门一条用例）；IndexedDB 故障时回应失败态而不是抛错；清空后同一段原文的翻译重新走上游请求且落定形态不变。
- **配置页**：既有 `tests/options.test.js` + `tests/helpers/options-sandbox.js`（解析真实 `options.html`、存储替身、每用例干净模块实例）。需要给该沙箱的 chrome 替身补 `runtime.sendMessage` 替身（现有替身只有 `storage`），并把发出的消息记入可观测列表。新用例：点击按钮恰好发出一条 `clear-cache`、状态栏文案含条数、失败态文案、不写任何存储（`syncWrites` 为空）。
- 先红后绿；`npm test` 全绿后由收尾的 docs 票按**实测**用例数更新 `AGENTS.md`。
- 变异验证点分两处，各自在自己的层承力：给 background 的 `clear-cache` 分支加上「缓存关闭就不清」的守卫，background 侧的「开关无关」用例必须转红；给配置页的发送处加上「复选框未勾选就不发」的守卫，配置页侧的「开关关闭仍发出」用例必须转红。两处合看才是 D6 的完整覆盖——配置页的用例用的是自己的 `runtime.sendMessage` 替身，不会因为 background 加了守卫而变红，反之亦然。

## Out of Scope

- 按指纹或按条件的选择性清空（D1 的备选，留作将来）。
- 单个条目的浏览 / 删除 / 编辑 UI，以及缓存命中率、条数等统计面板。——**部分搬进范围**：整库条目分页浏览、总条数与每条累计命中次数由 cache-inspection 落地；单条删除 / 编辑、全局命中率与独立统计面板仍在范围外（见 `.scratch/cache-inspection/spec.md`）。
- 清空确认弹窗、撤销、清空历史审计。
- 作废在途请求写入的屏障（生成代数计数，D8 的备选）。
- 自动过期与 LRU 淘汰逻辑本身的变更——既有 D6/D7 照旧。
- 缓存条目的导入导出、跨设备同步。

## Further Notes

- 决策来源：本功能的 grilling 十问（Q1–Q10），全部按推荐答案落地；决策边界（清空范围、开关无关、失败可见）已同步进 `CONTEXT.md` 的「短文本缓存」词条与 `docs/adr/0008-short-text-cache.md` 的 Evolved 段。
- 与既有文档的关系：本功能把旧 spec 的 Out of Scope 条目「手动清空缓存的 UI 按钮」搬进范围；ADR-0008 的 D10 由「缓存故障永不表现为页面可见错误」收窄为「翻译流程中的故障静默降级；用户显式要求的手动清空必须回报成败」。
- 风险记录：清空与在途写入的竞争会产生条目复活（D8），这是明确的取舍而非缺陷；要消除它需要一套比清空按钮本身大得多的机制。
- 存储模块的 `clear()` 与 `cleanup()` 是两条独立路径：前者按用户意图清空一切，后者按配置删过期 + 淘超限；两者共用同一份 schema 常量，不共用逻辑。
